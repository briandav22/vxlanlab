The flow record

Each question below is something a fabric team, a security team or an app owner asks about the data center. The left verdict is what a collector that reads only the outer header can say about the spines. The right is with Kentik's VXLAN decode. Every row is reproducible with the lab: the inject to turn on and the query to run are underneath.

The hypothesis

Most data centers built in the last decade run an EVPN-VXLAN fabric. In those fabrics, every link between leaves and spines carries tunnels, so the conversations on them are hidden from any tool that reads only outer headers. If a customer exports sFlow from their fabric, Kentik can restore those conversations, and that answers questions the network team can't answer today.

We think this is valuable. The point of this section is to be able to explain it, demo it and test it with a customer before we lead with it.

Why sFlow, and only sFlow

sFlow copies the first bytes of the raw packet, so the VXLAN header and the whole inner packet ride along in every sample. NetFlow and IPFIX build a record from a flow cache keyed on the headers the switch routes on. On a spine, that's the outer header, and the inner one is gone before anything is exported.

Per the Kentik KB, VXLAN decode requires sFlow, reads the first 128 to 256 bytes of each sampled packet, and supports VXLAN only (GRE/NVGRE and GENEVE are listed as future).

Two ways Kentik decodes it

The device's type in Kentik picks the mode:

  • sFlow Tunnel Decode: inner IPs and ports become the normal Source/Destination dimensions. VNI and VTEP go in VXLAN dimensions. Existing dashboards, filters and alerts work on spine traffic unchanged.
  • VXLAN: inner fields go into VXLAN dimensions (VXLAN VNI 0/1 IP Address, Port, Protocol, VXLAN VNI 0/1, VXLAN VTEP 0/1 IP Address), stored as custom fields. Good for showing outer and inner side by side.

Source: kb.kentik.com/docs/using-vxlan and /device-specific-dimensions.

Who cares

  • Data center network team: which tenant, app or host is filling a spine; why ECMP is uneven; capacity per VRF.
  • Security and segmentation: proof that VRFs stay isolated, and an alert when two tenants start talking across the fabric.
  • App owners: the real path and volume of their east-west dependencies (web → db, ETL → lake).
  • Edge and NOC: following an internet customer or a DDoS from the border into the fabric to the server.

Qualify it with a customer

  1. Do you run EVPN-VXLAN? Which vendor and how many leaves and spines?
  2. Do the fabric switches export sFlow today, or only NetFlow/IPFIX?
  3. Is sFlow enabled on the spines and leaf uplinks, not just server ports? What header length?
  4. How do VNIs map to tenants or VRFs? Is that in a source of truth we can import?
  5. What's the question you can't answer about the fabric today?

Prove it on their data

  1. Pick two spines and one leaf pair. Confirm sFlow with 128-byte headers reaches Kentik.
  2. Set those devices to sFlow Tunnel Decode (or VXLAN for the side-by-side).
  3. Run "who is using this spine" before and after. Screenshot both.
  4. Map VNIs to tenant names with a custom dimension.
  5. Pick one of their real questions from the qualify list and answer it live.

What it can't do

  • No latency, loss or jitter. Flow counts traffic; it doesn't time it.
  • Nothing inside encrypted tunnels (IPsec, SD-WAN, TLS payloads).
  • No VM-to-VM traffic that never leaves a host.
  • Sampling misses some small flows. 1:4096 or more is common in fabrics.
  • Summing leaves and spines counts each packet more than once. Pick one tier for totals.
