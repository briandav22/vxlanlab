vxlanlab · demo guide

The spines carry everything and know nothing

This guide covers the whole vxlanlab project: a simulated VXLAN EVPN fabric that sends real sFlow and answers SNMP, so you can show how Kentik turns tunnel traffic back into servers, apps and tenants. It focuses on the 22-switch 5-stage fabric, and the smaller 3-tier lab works the same way.

Repo briandav22/vxlanlab Primary topology 5stage (site "VXLAN Lab DFW1") Collector Kentik Universal Agent, UDP 9995

1 · The problem

Why VXLAN hides the conversation

A VXLAN fabric carries tenant traffic between switches inside a tunnel. That is great for the network and bad for anyone who wants to know who is talking.

Overlay: the cars

The tenant traffic: real servers and apps, like web-01 10.10.1.21 talking to db-01 10.10.2.45. It rides inside the tunnel, and the VNI says which tenant network it belongs to.

Underlay: the road

The physical fabric: switches and their VTEP addresses, like tor_c 10.255.1.43 to tor_g 10.255.1.47. Its only job is to carry tunnels between switches on UDP 4789.

When a packet enters the fabric, the ingress switch (the VTEP) wraps it in a new outer header addressed VTEP to VTEP. Every device in the middle forwards on that outer header. So does every flow tool that reads only the first IP header it finds. This is what one sampled packet of the elephant backup looks like on a spine link:

2 · The value

What sFlow Tunnel Decode solves for

Kentik reads the packet header inside each sFlow sample, steps past the VXLAN header, and records the inner packet. Per the Kentik KB, Using VXLAN, you pick the behavior with the device Type in its general settings.

Device typeInner IPs and ports land inVNI and VTEP land inUse it for
sFlow Tunnel DecodeThe standard Source / Destination IP and Port dimensionsVXLAN dimensionsDay to day. Every dashboard, filter, alert and custom dimension built on Src/Dst IP starts working on spine traffic with no changes.
VXLANVXLAN dimensions (VXLAN VNI 0/1 IP Address, Port, Protocol)VXLAN VNI 0/1, VXLAN VTEP 0/1 IP AddressTeaching. The standard IP dimensions keep showing the underlay, so you can show before and after in one query (verify this in your portal).

What it gives the customer

  • Attribution on the busiest links. Spines and superspines carry the most traffic and, without decode, explain the least. Decode names the servers, ports and tenants on every fabric link.
  • Tenant and segment accounting. The VNI tells you which tenant network a flow belongs to (here, L3 VNI 50010 for PAYMENTS and 50020 for ANALYTICS), so you can measure share, chargeback and noisy neighbors.
  • Segmentation proof. Inner IPs crossing between tenants on a spine is a hole in your segmentation, visible as it happens.
  • One mental model. With Tunnel Decode, the inner IPs flow into the same dimensions as the rest of the network, so enrichment, custom dimensions and AI Advisor all work on fabric traffic too.

Why sFlow, and what it needs

  • sFlow ships the raw packet header, so the inner packet is in the sample. A NetFlow or IPFIX cache on a spine is keyed on the outer header and has already thrown the inner one away. Per the KB, VXLAN decode requires sFlow.
  • The sampled header must be long enough. A VXLAN-wrapped TCP packet needs 104 bytes of headers. The lab samples 128 bytes, a common switch default.
  • VXLAN is the only tunnel decoded today, per the KB. GRE, NVGRE and GENEVE are not.

What it can't do. No latency or loss, nothing inside encrypted tunnels, no VM-to-VM traffic that never leaves a host, and small flows can be missed by sampling. Kentik also counts a packet once per device that samples it, so pick one tier (for example the spines) for totals.

4 · Run it

Stand it up and turn scenarios on

Run the lab on the same Linux host as the Universal Agent (a 2 vCPU / 4 GB droplet is plenty). The fake switch IPs live on loopback, so the agent sees each one as a separate exporter.

  1. Get the code
git clone https://github.com/briandav22/vxlanlab.git && cd vxlanlab
# already cloned:
cd ~/vxlanlab && git checkout main && git pull
  1. Put credentials and IDs in an env file. Every line needs export and straight quotes. Plan, agent and credential IDs come from the portal you are onboarding into. KENTIK_SNMP_CREDENTIAL is the name of an SNMP v2c credential (community public) saved in Kentik's credential vault.
cat > ~/.kentik.env <<'EOF'
export KENTIK_EMAIL="you@example.com"
export KENTIK_API_TOKEN="YOUR_TOKEN"
export KENTIK_PLAN_ID="1234"
export KENTIK_AGENT_ID="5678"
export KENTIK_SNMP_CREDENTIAL="NAME_OF_SNMP_CREDENTIAL"
export VXLANLAB_TOPOLOGY=5stage
EOF
chmod 600 ~/.kentik.env
source ~/.kentik.env
  1. Add the switch IPs to loopback. Needed again after every reboot. "Address already assigned" errors are harmless.
sudo -E python3 -m vxlanlab aliases --apply
  1. Onboard the 22 devices into a new site with all five layers. Safe to re-run: existing devices are updated, not duplicated.
python3 -m vxlanlab kentik onboard --site-name "VXLAN Lab DFW1" --dry-run   # preview
python3 -m vxlanlab kentik onboard --site-name "VXLAN Lab DFW1" -v
  1. Create the custom dimensions from vxlanlab/subnets.csv (see section 8).
python3 -m vxlanlab kentik dimensions --dry-run
python3 -m vxlanlab kentik dimensions
  1. Turn on decode in the portal: set each device's Type to sFlow Tunnel Decode (or VXLAN on one spine for a teaching contrast). The onboarding script creates them as plain routers.
  2. Start the fabric. Use tmux so you can type scenario names during the demo and detach afterwards.
tmux new -s lab
sudo -E python3 -m vxlanlab run --collector 127.0.0.1 --port 9995 --snmp
# Ctrl-b d to detach, tmux attach -t lab to come back

Give it 15 minutes before a demo so Kentik has a baseline to compare against.

5 · Use cases

Demo scenarios and talk tracks

Each scenario is a real problem that looks like nothing, or like the wrong thing, without decode. A strong sequence is surge (outside in), then elephant (east-west), then leak (security), which covers ops, capacity and security on one fabric.

Hot path from one backup

elephant
What happens
A 2.5 Gbps nightly backup from db-01 10.10.2.45 (pod 1) to backup-01 10.10.5.50 (pod 2) on one TCP session, port 10566, routed in L3 VNI 50010. One 5-tuple hashes to one path: tor_c › leaf_b › spine_b › superspine_b › spine_d › leaf_f › tor_g.
Use case
"The app is slow, but utilization looks fine." ECMP can't split one conversation, so one path runs hot while its siblings idle.
Without decode
One fat tunnel, 10.255.1.43 → 10.255.1.47 on UDP 4789. Indistinguishable from every other tor_c to tor_g conversation.
With decode
db-01 → backup-01 on 10566, VNI 50010. Which app, which tenant, which servers.
Who it lands with
Data center and network ops teams fielding "it's the network" tickets; anyone running backups, storage replication or AI/ML training across a leaf-spine fabric.

Talk track

  1. "The app team says the app is slow. Average utilization says everything's fine."
  2. "Look at the links themselves." On the map, one path is hot and its parallel links are quiet. That imbalance is the clue.
  3. "Without decoding VXLAN, all you see is tor_c talking to tor_g on 4789." Filter 10.255.1.43 → 10.255.1.47.
  4. "With Kentik's decode, we see inside the tunnel." Filter 10.10.2.45 → 10.10.5.50, port 10566.
  5. "Now it's a conversation with the backup team, not the network team: move the window, rate-limit it, or tune hashing."

Tenant segmentation breach

leak
What happens
Someone leaks routes between VRFs. PAYMENTS web servers (10.10.1.21-23) start reaching ANALYTICS etl-02 10.20.3.31 and lake-02 10.20.4.41 on tcp 9092, about 25 Mbps per pair, across the fabric in VNI 50020 (replies in 50010).
Use case
Compliance and segmentation (PCI, tenant isolation). Prove tenants stay apart, and catch the moment they don't.
Before the leak
Only a trickle of web-01 → etl-01 10.20.3.30 on 9092, seen at tor_a with no VNI. That's an attempt the switch dropped.
The rule to teach
PAYMENTS → ANALYTICS with no VNI is an attempt. PAYMENTS → ANALYTICS with a VNI on a spine is crossing the fabric, and segmentation has a hole.

Talk track

  1. "Your VNIs are supposed to keep these tenants apart. Here's PAYMENTS to ANALYTICS for the last hour: almost nothing, and it never left the first switch."
  2. Turn on leak. "Nothing in the underlay changed. Same VTEPs, same UDP 4789. Only the inner headers say two tenants just started talking."
  3. "This is the query to save as an alert."

Noisy neighbor

noisy
What happens
ANALYTICS kicks off a full lake rebuild: lake-01/02 (10.20.4.40-41) → etl-01/02 (10.20.3.30-31) on tcp 50010, 64 parallel streams per server pair, about 1.6 Gbps, routed in L3 VNI 50020.
Use case
One tenant's batch job hurts everyone else's app. Many 5-tuples, so ECMP spreads it over every tier, unlike the elephant.
Without decode
"Everything went up." No way to say whose traffic it is.
With decode
VNI 50020 swells on all spines, and the Src Tenant dimension says ANALYTICS. Chargeback or rate-limit the right tenant.

The rebuild's destination port, 50010, happens to match the PAYMENTS L3 VNI number. Don't let it confuse a filter: port 50010 is ANALYTICS traffic, VNI 50010 is PAYMENTS.

Internet surge into the fabric

surge
What happens
About 1.2 Gbps of small UDP packets from up to 2,000 internet sources (203.0.113.0/24, 192.0.2.0/24) aimed at web-01 10.10.1.21 on UDP 443, entering through both edge_a and edge_b.
Use case
"Is this a launch or an attack?" Your edge already sees it. Decode follows it into the fabric: which edge, which superspine, which ToR, which server.
With decode
Outside IPs visible on spine and superspine links, inside the tunnel, with Kentik's geo and ASN enrichment applied (verify for your portal that enrichment runs on decoded inner IPs).

Why they matter in a VXLAN demo

  • They're the before and after in one column. Without decode, every spine flow matches only the VTEP range, so Src Tenant reads UNDERLAY and Src Role reads vtep. With sFlow Tunnel Decode, the same flows match the inner subnets and read PAYMENTS / web or ANALYTICS / lake.
  • Tenant turns "VNI 50020" into "ANALYTICS", which is what a customer recognizes. It's the dimension for share-of-fabric, noisy neighbor and the leak alert (Src Tenant PAYMENTS, Dst Tenant ANALYTICS).
  • Role draws the application dependency map: web → db, db → backup, etl → lake, internet → web.
  • Segment splits a tenant into its VLANs, useful when one segment (anl-lake during noisy) is the problem.
  • Zone separates north-south (external → overlay) from east-west (overlay → overlay), and shows how much traffic is plain underlay or management.

How the lab builds them

python3 -m vxlanlab kentik dimensions reads vxlanlab/subnets.csv and, through the Kentik v5 API:

  1. Looks up each of the eight dimensions by name and creates only the missing ones (string type, display names like "Src Tenant").
  2. Groups the CSV by value, so each value is one populator whose address list holds all of its subnets. UNDERLAY is one populator with six ranges.
  3. Sends each dimension's populators in one batch call with replace_all, direction src for c_src_* and dst for c_dst_*. Each dimension ends up holding exactly what the CSV says, so it's safe to re-run after editing the CSV. Anything added by hand to these eight dimensions is removed.
  4. Spaces calls a second apart (--delay) and retries HTTP 429 with backoff.

Populators only tag flows that arrive after they exist. Create the dimensions, then let the lab run before demoing them. Use --api-url https://api.kentik.eu/api/v5 for an EU portal.
